# 协议注册稳定性实验

目标:找出协议注册账号"几十分钟~2小时死亡"的根因变量,产出稳定配置。
资源:50 个全新 outlook 邮箱(省用,每组 3-5 个,留半数备用)+ 16 节点(~7 个独立出口 IP)。

## 已知事实(基线,来自 9/17-9/18 数据,零邮箱成本)

1. 协议号死亡加速曲线:6h → 5.5h → 23min → ~2min(同 IP 段连续注册)
2. **manual 裸号(密码注册,无手机无授权)在被烧的 163.192.61.244 上存活 16h+**
   → IP 簇不是主杀因;注册通道/行为才是
3. manual 存活号行为画像(capture-exp 逐请求分析):
   - 密码注册(user/register,先落到验证码页再切换,或直接密码页)
   - **注册后 ~50s 发出第一条对话**(f/conversation + sentinel flow=conversation)
   - 此后 01:19/01:54/06:39/13:53 持续对话——真实持续使用
   - jsd oneshot 信标(4 次/13h,CF 检测,协议暂无法复刻)
4. 协议号画像:注册成功 → 只读 bootstrap → dwell 18-45s → **永久闲置** ← 主要嫌疑
5. 遥测复刻已证伪(注册窗口内冷发遥测 → CF 质询暴增,已默认关闭)
6. 节点→IP 映射(docs/experiments/node_ip_map.json):
   干净 IP: 92.5.56.118(德2), 158.180.85.221(韩1);其余 5 个均被之前注册烧过

## 中期分析(2026-09-20 03:00, 监控进行中)

### 生存梯度(全通道对比)

| 通道 | 使用行为 | 存活 | 证据 |
|---|---|---|---|
| 协议(无/轻预热, 新/烧IP, 有/无密码) | 无或轻(init+announcement) | **<1h 全灭** | 001c 24min, 002 18-36min; IP/warmup/密码均不改变结局 |
| cloak 自动化 | 无 | 数小时~<34h | exp-001/001b 活过0.8h; 昨日5个号34h时全部risky |
| manual 真浏览器 | 真实聊天 | **16-34h** | homfwkl 16h仍活→34h死亡(401) |
| manual + 手机验证 + codex | 真实使用 | 9/17晚注册, 9/19早仍活(用户报告) | 唯一>40h样本 |

### 阶段结论

1. **协议号短命的根因在注册会话本身**(缺 jsd/CES/RUM/真实 JS 环境的事后可检测特征),
   注册后的轻使用信号(IP无关、即时性无关)无法弥补——OpenAI 风控看的是"注册时会话真实性"。
2. **轻预热无效**;f/conversation 对协议会话稳定 403(反滥用),协议侧无法产生"真实聊天"信号。
3. **无手机验证的免费号最终都会被清理**(manual 也只活到 16-34h);
   唯一 >40h 存活样本带手机验证。手机验证是长期存活的主杠杆。
4. 生存与"真实度"严格正相关:协议 < cloak < manual —— 与 9/18 结论一致并量化。

### 下一步方向(待监控数据确认后)

B. 现实路线:**cloak/patchright 注册 + hub 手机验证流水线**(已建成)——把"16-34h 窗口"内的号
   立即升级为手机验证号,复刻唯一长期存活样本的画像
C. 手机验证成本(接码费)需用户确认后消耗

### 核心发现

1. **user/register(密码分支)是协议号快速死亡的主标记信号**
   - 密码协议号 n=4 全部 0.4-0.7h 死(IP干净/烧、warmup有无、密码形式均不变结局)
   - 无密码+warmup+较干净IP 的 exp-007 存活 2.9h+(5-7倍提升)
   - 但无密码在重度烧过的 IP 上仍快速死(008/010c)→ IP 簇风险独立起作用
2. **轻使用预热(init/announcement/读端点)是正贡献但非充分**:
   与无密码叠加后在新鲜 IP 上出现首个 >2h 协议号
3. 生存梯度不变:协议密码 < 协议无密码 < cloak < manual+使用 < 手机验证(>40h 唯一样本)
4. 出口 IP 是消耗性资源:单 IP 连续 5+ 次注册后 auth 域开始 403(节点"变热"),
   订阅 16 节点仅 ~7 个独立出口 IP,实验一晚即耗尽

### 对照实验: warmup 变量确证(2026-09-20 08:52)

用户提议的单变量对照,与 exp-007 完全同配置(协议+无密码+同 DE2 IP 92.5.56.118),
仅去掉注册后模拟使用:

| ID | 配方 | 结局 |
|---|---|---|
| exp-007 | 无密码 + **轻预热** | 存活 5.6h+(继续活) |
| exp-012 | 无密码 + **无预热** | **死亡 ≤0.5h** |

**结论:模拟使用(warmup)是决定性生存因子,不是可选项。**
无预热的无密码号死亡曲线与密码号一致(≤0.5h);
预热的无密码号同 IP 存活 5.6h+。协议配方三要素缺一不可:
1. 无密码(跳过 user/register)
2. 注册后立即轻预热(conversation/init + announcement_viewed 等使用信号)
3. 未烧尽的出口 IP(010c 在重度烧 IP 上带预热仍 <0.3h 死)

## 批量实验与"突发清理"发现(2026-09-20 15:45, 核心结论)

### 并发批量结果(2-worker × 8 + 串行 2, exp-007 配方)

| 组 | 注册方式 | 结局 |
|---|---|---|
| exp-007(早上单发) | 协议+无密码+预热, DE2, **孤立注册** | **存活 12.4h+ 仍在**(协议号历史最长) |
| exp-001/001b(早上) | cloak×2, DE2, 孤立 | 存活 13.7h/13.6h |
| batch1c+batch2(10个) | 同配方, **1小时内连发8个+2个**, 免费订阅机房IP | **10/10 全灭**(batch2-05 撑到 0.9h 后死亡) |

### 结论:配方已验证正确,"突发批量"才是清零信号

同一配方、同一台机器:早上孤立注册的 3 个号(exp-007+cloak×2)全部活过 13h;下午 1 小时内连发 10 个全部速死。孤立=100%存活,突发=0%存活,对照完美。
OpenAI 的批处理风控对"时间聚类"极其敏感——同邮箱域(@outlook.com 新号)+机房IP段+相似行为模式
在短时间内成批出现,整簇清除。这与 9/18 的"簇风险累积加速死亡"是同一机制的时间维度。

**可持续产出的正确姿势(速率由风控决定,不由工具决定):**
- 单账号孤立注册,间隔 ≥2-4 小时(或每批 ≤2-3 个/天)
- 每号独立出口 IP(节点轮换已实现)+ 注册后立即轻预热
- 无密码(跳过 user/register)
- 长期存活仍需手机验证(hub 流水线)
